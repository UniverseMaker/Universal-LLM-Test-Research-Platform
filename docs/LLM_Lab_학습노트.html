02

LLM은 상태가 없다 (매 턴 전체 대화 전송)

가장 근본적인 사실: LLM은 상태(state)가 없습니다. 모델은 한 번의 forward pass에 들어온 토큰만 봅니다. 요청 사이에 "기억"을 저장하지 않아요. 그래서 대화가 이어지는 것처럼 보이는 건 앱이 매 질의마다 지금까지의 전체 대화를 다시 보내기 때문입니다.

이게 표준입니다(OpenAI·Anthropic·vLLM 모두). 서버가 무상태라 아무 요청이나 아무 GPU로 보낼 수 있고(확장성), 클라이언트가 무엇을 보낼지 완전히 제어합니다. 대신 두 가지를 이해해야 합니다:

  • 비용·지연 누적: 대화가 길수록 입력 토큰이 계속 커집니다. 그래서 실무는 sliding window(최근 N턴), 요약 압축, RAG형 메모리로 관리합니다.
  • Prompt caching: 매번 전체를 보내도, 서버는 바뀌지 않은 앞부분의 내부 계산(KV cache)을 재사용합니다. vLLM의 automatic prefix caching 덕에 같은 세션 연속 질의는 계산 비용이 크게 완충됩니다(입력 토큰 수 자체는 그대로).
  • Context window: 전체 히스토리가 모델 한도(예: Gemma 131072 tok)를 넘으면 잘리거나 오류. 인스펙터 게이지로 사용량을 봅니다.
핵심
"멀티턴 대화" = 매번 전체 히스토리를 재전송하는 착시. 새 세션을 시작하면 히스토리가 리셋됩니다. LLM Lab의 인스펙터 request 탭에서 실제로 몇 개 턴이 실려 갔는지 눈으로 확인할 수 있습니다.
03

요청 읽는 법 — 지표와 샘플링 파라미터

LLM Lab의 인스펙터는 각 요청을 4개 축으로 보여줍니다: request(URL·모델·헤더·messages), response, timing, usage. 성능 지표의 의미:

  • TTFT (Time To First Token): 요청부터 첫 토큰까지. 프롬프트 처리(prefill) 지연을 반영 — 긴 컨텍스트일수록 커짐.
  • tok/s (throughput): 초당 생성 토큰 수. 디코딩 속도.
  • usage: prompt_tokens(입력) · completion_tokens(출력) · total_tokens. 비용·컨텍스트 관리의 근거.

생성을 제어하는 샘플링 파라미터(엔지니어 상세설정에서 조정, extra_body로 확장):

06

두 검색기의 상보성 · BEIR

렉시컬 BM25 · sparse

  • 정확한 단어·용어 일치
  • 고유명사·코드·ID·에러코드
  • 학습 불필요, 도메인 강건
  • 동의어·의역은 못 잡음

시맨틱 Dense · embedding

  • 의미·문맥 유사(동의어·의역)
  • 어휘 불일치 해소
  • 학습 도메인 밖 성능 저하
  • 희귀어·중의성에 약함

BEIR(Benchmarking-IR, 이기종 정보검색 제로샷 벤치마크) 벤치마크[2](18개 데이터셋)의 핵심 결과: BM25(Best Matching 25, 확률 기반 렉시컬 랭킹 함수)는 강건한 베이스라인이며 Dense 모델이 다수 OOD(out-of-domain, 학습 도메인 밖) 태스크에서 BM25에 밀린다. 어떤 단일 방식도 모든 도메인을 못 이깁니다 → 렉시컬 + 시맨틱을 융합하는 하이브리드의 실증적 동기입니다.

07

점수 vs 순위, 그리고 RRF 공식

RRF 란
RRF = Reciprocal Rank Fusion(상호 순위 융합). 여러 검색기의 결과 목록을 각 문서의 순위(rank)만으로 합치는 융합 기법입니다. "몇 점이냐"(점수 크기)가 아니라 "몇 등이냐"(순위)만 쓰는 것이 핵심 — 그래서 척도가 다른 검색기도 정규화 없이 합쳐집니다. Cormack 등(2009)이 제안[4].

두 점수는 척도가 다릅니다 — BM25는 상한 없는 양수(3~40+), 코사인은 0~1. 그냥 더하면 BM25가 지배합니다. 점수 기반 결합은 정규화(min-max·z-score)가 필수인데, 실무 통찰은 "방식보다 정규화 여부가 1차 문제"라는 것[3]. RRF(Reciprocal Rank Fusion)는 아예 점수를 버리고 순위만 써서 이 문제를 회피합니다.

순위는 1부터. 여러 검색기에서 두루 상위인 문서일수록 합이 커져 위로 올라옵니다 — RRF는 합의를 보상합니다. Cormack 등(2009)이 제안[4].

09

RRF의 대안들 · 비교표

RRF는 순위만 써서 점수 간격 정보(1등이 근소차인지 압도차인지)를 버립니다. 이를 되살리거나 상한을 높이는 대안들:

CombSUM / MNZ

점수
MNZ = Σsᵢ × (등장 리스트 수)

CombSUM = Combination SUM. 정규화 점수 합산. MNZ = Multiply by Non-Zero — 여러 검색기가 공통으로 찾은 문서에 가산점.[5]

점수 보존 · 정규화 민감

볼록결합 (CC)

점수
α·norm_dense + (1−α)·norm_lex

CC = Convex Combination. Bruch 등(2023): CC가 RRF를 in/out-domain 모두 능가, ~40개 라벨로 표본효율적[6].

상한 최고 · 라벨 필요

relativeScoreFusion

점수
min-max 정규화 후 가중합

Weaviate: 점수 간격 보존, 재현율 +6%, v1.24 기본값[7].

간격 보존 · 배치 의존

DBSF

점수
경계 = μ ± 3σ

DBSF = Distribution-Based Score Fusion(분포 기반 점수 융합). 이질·멀티모달 결합에 강건[8].

이질분포 강건 · 소표본 불안정

Borda / Condorcet

순위
선형 순위점수 / 쌍대 다수결

순위 투표(선거 이론에서 유래). Condorcet은 정확하나 O(n²)[9].

단순 · 대개 RRF 우위

LTR (LambdaMART)

학습
임의 피처 → nDCG 최적화

LTR = Learning-to-Rank(순위 학습). 지도학습 결합, 상한 최고지만 라벨·파이프라인 필요[10].

상한 최고 · 무거움
한 줄 결론
라벨 없음·다도메인 즉시배포 → RRF. 도메인 고정+소량 라벨 → CC/relativeScore. 대규모 클릭로그 → LTR. "기본은 RRF, 여유되면 점수기반과 A/B"가 정석. 융합 뒤 리랭커(§11)로 직렬 정밀화도 가능.
10

무엇으로 재나 — 평가지표

"어떤 융합이 낫다"는 주장은 지표 위에서만 의미가 있습니다. 순위 무관(Precision@k, Recall@k) vs 순위 인식 — MRR(Mean Reciprocal Rank, 평균 역순위), MAP(Mean Average Precision, 평균 정밀도), nDCG(normalized Discounted Cumulative Gain, 정규화 할인 누적이득). 가장 널리 쓰는 nDCG:

상위일수록 log₂(i+1)로 할인하고, IDCG로 나눠 정규화하므로 질의 간 비교가 됩니다[11]. 하이브리드·리랭킹 품질은 보통 nDCG@10 + Recall@k를 함께 봅니다. LLM Lab의 Eval 워크벤치(§14)가 이런 비교를 돕습니다.

11

융합 다음: 리랭킹 (2단계)

융합과 리랭킹은 배타적이 아니라 직렬입니다. 융합은 리스트를 합치고, 리랭커는 후보 top-N을 정밀 재정렬합니다.

bi-encoder는 질의·문서를 따로 인코딩해 빠르지만 정밀도가 낮고, cross-encoder는 함께 넣어 정밀하나 느립니다 → 속도(1단계)×정밀도(2단계)로 분리. 중간이 ColBERT(late interaction, 토큰 MaxSim)입니다[12]. 2단계로 nDCG@10이 통상 5~15점 오릅니다(데이터셋 의존).

12

하이브리드 검색 vs GraphRAG

하이브리드는 평면 청크에서 지역적 관련성을 극대화합니다. 하지만 "코퍼스 전체의 주요 테마는?" 같은 전역 질문은 검색이 아니라 질의 초점 요약이라, 축이 바뀝니다. GraphRAG[13]는 엔티티·관계를 추출해 지식 그래프를 만들고, Leiden 커뮤니티로 군집화해 요약한 뒤 map-reduce로 전역 질문에 답합니다.

Part IV

에이전트 · 평가 · 시뮬레이션

도구를 쓰게 하고, 좋고 나쁨을 재고, 모델끼리 대화시킨다

13

ReAct 에이전트 · 툴

에이전트는 LLM이 스스로 도구(tool)를 골라 호출하고 결과를 보고 다음 행동을 정하는 것입니다. 대표 패턴이 ReAct(Reasoning + Acting)[14] — 생각과 행동을 번갈아 반복합니다.

Thought
무엇을 할지 추론
→
Action
도구 호출(검색·계산…)
→
Observation
도구 결과 관찰
↻ 답이 나올 때까지 반복 → Final Answer

LLM Lab의 Agent 워크벤치는 이 루프를 실행하고, 각 단계의 Thought/Action/Observation을 트레이스로 보여줍니다. 도구는 계산기·검색 등 내장 도구를 쓰거나 정의할 수 있습니다. 핵심 한계: 루프가 길어지면 컨텍스트가 누적되고(비용↑), 잘못된 관찰에 빠지면 회복이 어렵습니다 — 그래서 반복 상한·검증이 중요합니다.

14

평가 · LLM-as-Judge

모델·프롬프트가 실제로 나은지 재려면 체계적 비교가 필요합니다. LLM Lab의 Eval 워크벤치가 지원하는 것:

  • A/B 비교: 두 모델(또는 프롬프트)에 같은 입력을 주고 출력을 나란히.
  • N회 반복: 같은 프롬프트를 여러 번 돌려 변동성(temperature 영향)을 관찰.
  • diff: 출력 간 단어 단위 차이를 강조.
  • LLM-as-Judge: 제3의 모델에게 "어느 답이 더 나은가"를 채점시켜 자동 평가. 저렴하고 확장 가능하나 위치 편향·자기선호 편향에 주의[15].
연결
검색 품질은 §10의 nDCG 같은 지표로, 생성 품질은 judge나 사람 평가로 잽니다. 재현성을 위해 평가 시 temperature를 낮추고 프롬프트·모델·파라미터를 인스펙터로 고정 기록하세요.
15

시뮬레이션 (모델 vs 모델)

Simulate 워크벤치는 두 모델(또는 두 페르소나)이 서로 대화하도록 자동 진행합니다 — 한쪽 출력이 다른 쪽 입력이 되는 루프. 용도: 대화 능력·일관성·안전성 관찰, 레드팀(공격자 vs 방어자), 협상·역할극 시나리오, 데이터 생성. 매 턴 전체 히스토리가 양쪽에 전달되므로(§02) 길어질수록 비용이 커지는 점을 유의합니다.

Part V

연결과 데이터

어떤 서버를 어떻게 연결하고, 실제 DB를 어떻게 붙이는가

16

API 연결 프로필 · 프록시 vs Direct

LLM Lab은 모델을 하드코딩하지 않고 연결 프로필로 관리합니다. 프로필 JSON은 service·base_url·model·auth.api_key·endpoints·params 등을 담고, 붙여넣기/파일로 import·export합니다(형식 정본은 프로젝트 docs/API_프로필_형식_가이드.md).

브라우저에서 외부 API를 부르는 두 경로:

Proxy 경유

  • 백엔드(/api/proxy)가 대신 호출·중계
  • CORS(교차 출처)·혼합콘텐츠 회피, SSE(Server-Sent Events) 스트리밍 중계
  • 서버(PHP/파이썬)가 있어야 함

Direct 호출

  • 브라우저가 API를 직접 호출
  • 정적 배포(백엔드 없음)에서 폴백
  • 단, https 페이지→http API는 혼합콘텐츠 차단
실전 함정
정적 호스팅엔 프록시가 없어 /api/proxy가 404 → 앱이 자동으로 direct 폴백. 또한 https 페이지에서 http API를 direct 호출하면 브라우저가 막으므로(혼합콘텐츠) https 엔드포인트를 씁니다. 이 프로젝트가 your-llm-server.example.com을 https로 표준화한 이유입니다.
17

실DB — RDB · pgvector · Neo4j

RAG를 실제 데이터로 돌리려면 DB가 필요합니다. 공유호스팅(장기 실행 프로세스 불가) 환경이라 백엔드는 PHP로, 요청당 처리 방식으로 구현했습니다.

RDB

관계형 DB

PHP PDO(PHP Data Objects)로 SQLite·MySQL·PostgreSQL 연결. 정형 데이터·메타·BM25용 텍스트.

pgvector

벡터 검색

PostgreSQL 확장. 임베딩 유사도(<->)로 Dense 검색.

Neo4j

그래프 DB

HTTP API(cURL)로 Cypher 실행. GraphRAG의 지식그래프.

Graceful 강등

확장 없으면

extension_loaded()로 감지해 미탑재 시 안내·목업으로 강등.

RAG Lab의 검색은 벡터 질의를 /api/db/vector/search(pgvector), 그래프 질의를 /api/db/graph/query(Neo4j)로 라우팅합니다. 확장이 없는 호스팅에서도 SQLite로 데모가 돌도록 자동 시드됩니다.

18

한눈에 — 학습 지도

이 노트를 한 문장으로 잇습니다:

전체 서사
모델은 상태가 없어(§02) 매 턴 전체 대화를 보낸다 → 한 호출로 부족하면 체이닝(§04–05)으로 나눈다 → 외부 지식이 필요하면 검색하고 렉시컬+시맨틱을 RRF로 융합(§06–09)한다 → 품질은 nDCG(§10)로 재고 리랭커(§11)로 정밀화한다 → 질문이 전역·관계적이면 GraphRAG(§12)로 간다 → 도구가 필요하면 에이전트(§13), 검증은 평가·시뮬(§14–15) → 이 모두를 연결 프로필(§16)과 실DB(§17) 위에서 돌린다.

각 주제는 LLM Lab의 해당 워크벤치에서 직접 실험할 수 있습니다 — 개념을 읽고, 인스펙터로 실제 요청을 확인하며 손으로 익히는 것이 이 플랫폼의 목적입니다.
